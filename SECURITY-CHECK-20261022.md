# Проверка безопасности от 22 октября 2026

На присланных изображениях показаны Pluck CMS 4.7.13, PHP/PHAR, MySQL и адрес 10.146.145.243. В PAPPARE используется Next.js/PostgreSQL. Изображения сами по себе не доказывают компрометацию PAPPARE; источник изображений и журналы VPS пока неизвестны.

## Изменения

- Next.js и eslint-config-next обновлены с 15.5.27 до 15.5.28. Обновлены оба lock-файла. Основание: https://nextjs.org/blog/nextjs-security-update-october-14-2026 . Sharp уже был не ниже 0.35.5.
- Middleware возвращает короткий 404 для PHP/PHAR и служебных .env/.git/.svn/.hg путей вместо полной отрисовки страницы. Это снижает стоимость таких сканирований, но не заменяет обновления, аутентификацию или защиту от распределённого отказа в обслуживании. Исключённые matcher пути API, assets и _next продолжают обрабатываться собственными маршрутами.
- Добавлен scripts/check-vps-security.cjs: только чтение, сводка PM2 без значений секретов, установленные версии, TCP-порты, nginx -t, UFW и агрегаты последних 10 000 строк стандартного access.log. Ротация и отдельные журналы сайта не включены. Версия в node_modules не доказывает, что работающий процесс уже перезапущен.

Проверены доступные публичные GET: / и /kino/admin отвечают 200, присутствует CSP, Cache-Control private/no-store, отсутствует X-Powered-By, Server не содержит версии. Открытая страница входа с HTTP 200 не означает доступ к административному API. Проверка паролей и реальные платежи не выполнялись.

## На VPS

Сначала получить изменения и собрать сведения:

```bash
cd /var/www/pappare &&
git pull --ff-only origin main &&
node scripts/check-vps-security.cjs
```

Если нет признаков реального постороннего доступа и двухфакторный вход уже настроен, обновить приложение:

```bash
cd /var/www/pappare &&
npm ci &&
npm run test:security &&
npm run test:cinema &&
npm run build &&
node scripts/restart-admin-security.cjs
```

При ошибке не выполнять следующие шаги вручную. Не присылать .env, pm2 jlist или вывод setup-admin-2fa.cjs: они содержат секреты. Скрипт check-vps-security.cjs выводит только выбранные безопасные поля. Числа рестартов, 401/429 или запросы к PHP сами по себе не подтверждают взлом. UFW inactive не учитывает внешний firewall провайдера; ss показывает привязку сокетов, но не доказывает их доступность из Интернета.

Если появились незнакомые SSH-входы, пользователи, процессы, cron-задачи или файлы, сначала сохранить снимок и журналы через хостинг. Исследовать сервер с поддержкой провайдера. При подтверждённой компрометации — восстановление на чистом сервере и ротация затронутых секретов из доверенной среды; обновление одного приложения не устраняет присутствие злоумышленника в ОС.

Защита SSH, внешние firewall, закрытие прямого доступа к Node/PostgreSQL и права системных пользователей требуют фактической конфигурации VPS. Автоматические изменения портов и firewall без этой информации не применялись.

## Закрытие прямого доступа к Node — следующий шаг

22 октября получено подтверждение локального upstream nginx на порту 3000, локальной привязки PostgreSQL и работающего приложения после обновления. Прямой HTTP GET к внешнему адресу сервера на TCP/3000 также получил 200.

Подготовлен `scripts/protect-backend-port.cjs` для запуска владельцем на VPS от root. Он проверяет nginx, локальную страницу входа и наличие iptables/ip6tables; добавляет только REJECT для входящего TCP/3000 с интерфейса, отличного от lo, в обеих IP-семьях. Не меняет политику цепочек, не очищает правила, не включает UFW, не закрывает SSH и не перезапускает приложение. Для повторного применения при загрузке создаёт собственный systemd unit и root-only helper в /usr/local/sbin. Проверены сценарии повторного запуска, ошибки сохранения и нездорового локального приложения с подменёнными системными вызовами; реальный firewall локального Windows-компьютера не менялся. На VPS скрипт ещё должен быть выполнен владельцем.

```bash
cd /var/www/pappare &&
git pull --ff-only origin main &&
sudo node scripts/protect-backend-port.cjs
```

После применения `ss` по-прежнему может показывать `*:3000`: запрет обеспечивается firewall. Нужно отдельно проверить сайт по HTTPS и отсутствие внешнего доступа к TCP/3000. UFW может оставаться inactive — эти правила устанавливаются независимо. При ручном сбросе правил, перезапуске других менеджеров firewall или изменении сетевой архитектуры необходимо проверить защиту заново. Правила INPUT не предназначены для опубликованных Docker-портов через FORWARD; текущая конфигурация использует Node под PM2 на хосте.

Только при необходимости ручного отката удалить собственный unit и два собственных правила (другие правила не трогать):

```bash
sudo systemctl disable --now pappare-backend-guard.service
sudo iptables -w 10 -D INPUT ! -i lo -p tcp --dport 3000 -m comment --comment pappare-backend-3000 -j REJECT --reject-with tcp-reset
sudo ip6tables -w 10 -D INPUT ! -i lo -p tcp --dport 3000 -m comment --comment pappare-backend-3000 -j REJECT --reject-with tcp-reset
```

При таком откате порт снова станет внешне доступным. Файлы unit/helper можно оставить выключенными. Исходные справочники: https://www.netfilter.org/documentation/ и https://www.freedesktop.org/software/systemd/man/systemd.service.html .
